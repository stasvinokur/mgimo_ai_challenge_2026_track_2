# Голос «Сводки дня»

Локальный Silero TTS `v5_5_ru`, PCM WAV: моно, 24 кГц, 16 бит.
Голос кабинета («Послушать») — мужской **`aidar`**. Диктор демо-видео —
женский **`xenia`**, чтобы в ролике голоса не сливались. Сервис принимает
только эти два голоса; если поле `voice` отсутствует, используется `aidar`.
Адаптер приложения всегда отправляет `aidar`, выбор голоса из клиентского
запроса не принимается. Ключ кэша приложения учитывает голос и текст фразы.
Сценарий видео обращается к тому же сервису напрямую с `voice: "xenia"`.
Python 3.12.16, PyTorch **2.15.0+cpu** из официального CPU-индекса. CUDA, numpy,
omegaconf и torch.hub не используются. Модель загружается через `torch.package`.

Модель: [Silero Models](https://github.com/snakers4/silero-models),
[файл v5_5_ru.pt](https://models.silero.ai/models/tts/ru/v5_5_ru.pt).
Лицензия весов — **CC BY-NC 4.0**: указание авторства Silero Team,
некоммерческое использование. Этот конкурсный прототип некоммерческий.
Размер файла — 145 420 684 байт. SHA-256:
`50081637b602126ee06cb3bc8a744d25651d2da149ee8864b9a379bfdd934437`.
Сборка прекращается при несовпадении хэша. Загрузка модели нужна только при
сборке; в работающем контейнере внешняя сеть отсутствует.

## Lock зависимостей

Lock создан **06.11.2026** для CPython 3.12, Linux amd64 и arm64 из одного
индекса `https://download.pytorch.org/whl/cpu`. В `requirements.txt` закреплены
все десять пакетов, включая транзитивные зависимости, и SHA-256. Docker
использует `pip install --require-hashes --no-deps --only-binary=:all: -r requirements.txt`:
исходные архивы и неявная установка новых зависимостей запрещены.

Обновление требует установленного `uv`; из корня репозитория выполните:

```sh
python3 infra/tts/update_lock.py
```

Скрипт читает `requirements.in`, разрешает обе Linux-архитектуры с
`--generate-hashes --only-binary=:all:` и одним `--index-url`, проверяет
совпадение полного набора версий и объединяет хэши. Lock перезаписывается
только после успешного разрешения обеих архитектур. Затем соберите образ и
выполните smoke на целевых архитектурах.

## Локальный запуск

В окружении приложения задайте `TTS_URL=http://tts:8000`. Запустите
`docker compose --profile tts up --build --wait`. Профиль необязательный:
без `TTS_URL` приложение использует голос устройства. В `compose.yaml`
порта наружу нет; приложение и tts общаются по отдельной сети `speech`
(`internal: true`). Только `app` и `tts` подключены к этой сети; доступа
к сети БД у `tts` нет.

Для приложения на хосте и `tools/demo-video.mjs` запустите отдельный
контейнер на обычной Docker bridge-сети. В `compose.dev.yaml` порт tts не
публикуется: публикация не работает для `internal: true`. Из корня проекта:

```sh
docker build -t pulse-tts-local infra/tts
docker run --rm -d --name pulse-tts-local --network bridge \
  --read-only --user 1001:1001 --cap-drop ALL \
  --security-opt no-new-privileges:true --cpus 2 --memory 1536m --pids-limit 64 \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m,uid=1001,gid=1001,mode=1770 \
  -p 127.0.0.1:8000:8000 pulse-tts-local
```

Для приложения на хосте задайте `TTS_URL=http://127.0.0.1:8000`; сценарий
видео обращается по тому же адресу с `voice: "xenia"`. Дождитесь состояния
`healthy` (`docker inspect --format '{{.State.Health.Status}}' pulse-tts-local`),
затем проверьте `docker exec pulse-tts-local python smoke.py`. Это отдельный
локальный запуск с доступом только через loopback хоста; рабочий compose и
CI используют закрытую сеть `speech` и не публикуют порт tts.
После работы: `docker stop pulse-tts-local`.

Проверка контейнера: `docker compose exec -T tts python smoke.py`.
Smoke проверяет WAV для `aidar`, `xenia` и запроса без голоса, а также 4xx
для цифр и неизвестного голоса. В JSON-запросе `POST /synthesize` передаются
`text` и необязательное поле `voice`.
Проверка валидации и очереди без torch: `python3 -m unittest discover -s infra/tts -v`.
Настоящий браузерный сценарий: `E2E_TTS=1 pnpm test:e2e tests/e2e/today-briefing-tts.spec.ts`.

## Ограничения и память

Одна синтезируемая фраза, две ожидающие в очереди; переполнение даёт 503.
Не более восьми HTTP-обработчиков. На чтение всей строки запроса, заголовков
и тела вместе даётся абсолютный дедлайн пять секунд: новые байты не продлевают
его. Просроченное чтение прерывается; ошибки разбора тела, включая слишком
глубокий JSON, дают 400. На результат синтеза — двенадцать секунд. Фраза — до шестисот символов, только русские
буквы, пробел и пунктуация `.,!?;:-–—`; цифры и прочие знаки отклоняются с 400.
Пустые/слишком длинные фразы и неизвестный голос тоже дают 4xx.
Текст, IP и тело запроса в логи не попадают; ошибки имеют фиксированные коды.

Контейнер ограничен двумя CPU, **1536 МиБ RAM**, 64 процессами и 64 МиБ tmpfs,
работает с uid 1001, read-only и без capabilities. Размер весов не равен RSS:
память также нужна PyTorch и промежуточным тензорам. На ревью 06.11.2026
для arm64 наблюдалось 703 МиБ из 1536; это контрольный замер прежнего образа.
Фактический пик RSS после пересборки нужно
измерить на целевой архитектуре (`docker stats --no-stream` во время синтеза);
замер внутри песочницы Codex недоступен. Приложение принимает максимум 4 МиБ
WAV за восемь секунд, хранит максимум 16 МиБ/64 фразы на одну минуту.

Лимит пары «пользователь + IP» расходуется на каждом допустимом запросе.
Общий предохранитель пользователя — только при промахе кэша перед сетевым
синтезом. Параллельные запросы одной фразы используют один результат;
ошибка квоты одного пользователя не передаётся другому. Неверная checksum
и запрос без `Sec-Fetch-Site: same-origin` не расходуют квоту.
